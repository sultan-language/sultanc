# Releases

A SultanC release is a set of prebuilt archives, one per host, built by CI from one tagged commit of
`master`. This page says what a release holds, how its version is set and how it is made.

## What a release holds

| Archive | Host |
| --- | --- |
| `sultanc-VERSION-x86_64-linux.tar.gz` | Linux x86_64 |
| `sultanc-VERSION-aarch64-linux-gnu.tar.gz` | Linux arm64 |
| `sultanc-VERSION-arm64-darwin.tar.gz` | macOS on Apple silicon |
| `sultanc-VERSION-x86_64-darwin.tar.gz` | macOS on Intel |
| `sultanc-VERSION-x86_64-windows-msvc.zip` | Windows x64 |

Each archive unpacks to one directory, `sultanc-VERSION-TARGET/`:

```text
bin/sultanc            the compiler
bin/supax              the package manager
bin/sultanc-analyzer   the language server (LSP)
library/               the standard library, found by the compiler next to bin/
LICENSE  README.md  INSTALL.txt
```

On Windows the programs end in `.exe`. On the hosts without a Native backend (Linux arm64, macOS on Intel,
Windows) the compiler is generated by LLVM and contains it, so the archive also holds the LLVM library:
`lib/` on Linux and macOS, `bin/LLVM-C.dll` on Windows. Beside the archives the release has one
`.sha256` per archive, `SHA256SUMS.txt` with all of them, and a build-provenance attestation of each
archive.

To install one: check it against `SHA256SUMS.txt`, unpack it and add its `bin/` to `PATH`
([README](../README.md#install)). `gh attestation verify ARCHIVE --repo sultan-language/sultanc` checks
that CI built it from the tagged commit.

## Versions

One number covers the toolchain: `sultanc`, Supax and sultanc-analyzer of a release all have it. The
compiler's version is written once, as `version` in `Supax.toml` (the package `sultanc`) and
`compiler/Supax.toml` (the library package `compiler`), and both must equal the tag: `v0.1.2` and the
candidate `v0.1.2-rc.1` both need `0.1.2`. A release build stamps the version through the build driver's
`--release-version` ([Bootstrap](../internals/bootstrap.md#buildsh)); `sultanc --version` then prints the
tag's version, the first 12 hex digits of the commit and the backends:

```text
$ sultanc --lang=en --version
SultanC 0.1.2+<the first 12 hex digits of the commit>
backends: native
```

A development build says `development` instead of a number. Supax and sultanc-analyzer are built from
the commits that `.github/ci/components.toml` pins, one per repository, which the owner fills in for each
release.

## How a release is made

1. The release commit sets the version and the pinned components, and is promoted to `master` like
   every commit, so it is qualified.
2. The owner tags it `vX.Y.Z-rc.N`, then `vX.Y.Z`. The tag starts `.github/workflows/release.yml`: it checks
   the tag, builds every archive from the tagged commit, waits for the owner's approval, and creates a
   **draft** release (a draft pre-release for `-rc.` tags). Its notes are the install steps followed by the
   notes GitHub generates from the changes since the last release; the owner edits them in the draft.
3. The owner checks the draft and publishes it. CI never publishes a release, pushes or moves a tag.
